# Оптимизация производительности базы данных

## Проблема

База данных медленно реагирует на запросы при большом объеме данных из-за:
1. **VARCHAR для ID**: Использование `VARCHAR(50)` для первичных ключей (`id_server`, `id_players`) замедляет JOIN операции и индексацию
2. **Недостающие индексы**: Отсутствие составных индексов для часто используемых запросов

## Решение

### 1. Изменение типов данных ID

**Проблема**: `VARCHAR(50)` для ID замедляет:
- JOIN операции (сравнение строк медленнее, чем чисел)
- Индексацию (индексы на строках занимают больше места)
- Поиск по первичным ключам

**Решение**: Изменение `id_server` и `id_players` с `VARCHAR(50)` на `BIGINT UNSIGNED`

**Примечание**: `id_profile` остается `VARCHAR(50)`, так как Telegram ID может быть строкой

### 2. Добавление индексов

Добавлены составные индексы для оптимизации часто используемых запросов:
- `idx_server_game` - для фильтрации серверов по игре
- `idx_profile_active` - для фильтрации активных профилей
- `idx_log_profile_date` - для фильтрации логов по профилю и дате
- И другие...

## Инструкция по применению

### Шаг 1: Проверка данных

Перед миграцией проверьте, можно ли конвертировать ID в числа:

```bash
python check_id_types.py
```

Скрипт покажет:
- Сколько записей имеют числовые ID
- Есть ли нечисловые ID (которые нельзя конвертировать)
- Максимальные значения ID

**Важно**: Если есть нечисловые ID, миграция не может быть выполнена автоматически.

### Шаг 2: Резервное копирование

**ОБЯЗАТЕЛЬНО** сделайте резервную копию базы данных перед миграцией:

```bash
python backup_database.py
```

Или используйте mysqldump:

```bash
mysqldump -u root -p bm_db > backup_before_migration.sql
```

### Шаг 3: Выполнение миграции

#### 3.1. Просмотр команд миграции (DRY RUN)

Сначала посмотрите, какие команды будут выполнены:

```bash
python migrate_to_bigint.py
```

Это покажет все SQL команды без их выполнения.

#### 3.2. Выполнение миграции

Если все выглядит правильно, выполните миграцию:

```bash
python migrate_to_bigint.py --execute
```

**Что делает миграция**:
1. Отключает проверку внешних ключей
2. Изменяет типы данных во всех связанных таблицах:
   - `servers.id_server`: VARCHAR(50) → BIGINT UNSIGNED
   - `players.id_players`: VARCHAR(50) → BIGINT UNSIGNED
   - Все внешние ключи, ссылающиеся на эти поля
3. Включает проверку внешних ключей обратно

**Время выполнения**: Зависит от объема данных. Для больших таблиц может занять несколько минут.

### Шаг 4: Добавление индексов

#### 4.1. Просмотр индексов (DRY RUN)

Посмотрите, какие индексы будут добавлены:

```bash
python add_performance_indexes.py
```

#### 4.2. Добавление индексов

Выполните добавление индексов:

```bash
python add_performance_indexes.py --execute
```

**Время выполнения**: Зависит от объема данных. Для больших таблиц может занять несколько минут.

### Шаг 5: Проверка результатов

После миграции проверьте производительность:

```sql
-- Проверка типов данных
DESCRIBE servers;
DESCRIBE players;

-- Проверка индексов
SHOW INDEX FROM servers;
SHOW INDEX FROM players;
SHOW INDEX FROM profiles_servers_conn;
```

## Ожидаемые улучшения

После применения оптимизаций:

1. **JOIN операции**: Ускорение в 2-5 раз за счет использования числовых ключей
2. **Поиск по ID**: Ускорение в 3-10 раз за счет более эффективных индексов
3. **Размер индексов**: Уменьшение на 30-50% за счет использования BIGINT вместо VARCHAR
4. **Общая производительность**: Улучшение на 40-70% для запросов с JOIN

## Откат изменений

Если что-то пошло не так, можно откатить изменения:

1. Восстановите базу данных из резервной копии
2. Или выполните обратную миграцию (не предоставлена, используйте резервную копию)

## Изменения в коде

После миграции код должен продолжать работать без изменений, так как:
- Python автоматически конвертирует числа в строки при необходимости
- Все запросы используют параметризованные запросы, которые работают с обоими типами

Однако, для лучшей производительности рекомендуется:
- Использовать числовые типы в Python коде для ID серверов и игроков
- Убедиться, что все ID конвертируются в числа перед запросами

## Технические детали

### BIGINT UNSIGNED

- **Диапазон**: 0 до 18,446,744,073,709,551,615
- **Размер**: 8 байт
- **Преимущества**: 
  - Быстрое сравнение (целочисленная арифметика)
  - Компактные индексы
  - Эффективные JOIN операции

### VARCHAR(50) для id_profile

Telegram ID может быть:
- Числовым (обычно)
- Строковым (для некоторых типов ботов)

Поэтому `id_profile` остается `VARCHAR(50)` для совместимости.
